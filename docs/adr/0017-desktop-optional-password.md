# ADR 0017 — 桌面模式的口令是可选项：不引导设置，凭桌面令牌可免旧口令设置

## 状态

已接受（2026-10-26）。修订 ADR 0016 决策 5（「首启引导优先」）。

## 背景

ADR 0016 引入桌面免登录时，为了防止「免登录把首次设口令短路掉」，规定 admin 处于锁定态（`password_hash = '!'`）时拒绝桌面令牌登录，并要求首启必须先在 `/bootstrap` 设口令。当时的判断是：口令是一道不该被绕过的基础门槛。

实测与反馈推翻了这部分判断：

- 桌面模式的日常登录完全不走口令（令牌 24h 会话 + 过期自动续），口令只在两种边缘场景有用：同一实例被远程/其他浏览器访问时的 admin 登录，以及切到 standalone 后的登录；
- 首启被强制设的口令，桌面用户之后基本不再输入，容易遗忘；遗忘后又没有 UI 自救路径（只有 CLI `--reset-password`），形成死路；
- 桌面端的信任边界是 OS 用户（ADR 0016 已论证），本地口令对本地攻击者没有增量保护，强制设置不换来实际安全收益。

## 决策

1. **桌面模式不引导设口令**：`desktop` 模式下 `ensure_admin` 不再签发引导令牌；admin 允许以「未设置口令」状态存在，首启直接经桌面令牌进入控制台。
2. **无口令 = fail-closed**：锁定态 admin 仍无法口令登录。桌面模式若同时对外监听，在设置口令之前**没有人能远程登录 admin**，因此去掉强制引导不扩大暴露面。
3. **口令改为控制台内可选设置**：`POST /api/auth/password` 允许在「`desktop` 模式 + 目标为 admin + 请求携带可验证的 `desktop_token`」时省略当前口令；其余情况一律要求当前口令。
4. **`desktop_token` 作为授权凭据**：与 `/api/auth/desktop` 同一套校验（本进程签发的 SHA-256）。令牌持有者 = 本机壳 = OS 用户，本就能换取完整 admin 会话，因此允许它设置口令不构成提权；设置动作写审计日志（不含口令）。
5. **`--reset-password` 语义不变但更好用**：把 admin 打回无口令后，桌面令牌仍可进入，用户可在控制台重新设置。
6. **`standalone` 完全不变**：首启仍强制引导设口令，改口令仍需当前口令，`desktop_token` 豁免在该模式下一律无效。
7. `/api/auth/me` 增加 `has_password`，让界面能区分「设置口令」与「修改口令」。

## 被否方案

- **保持现状（强制首启引导）**：用户必须先设一个几乎不会再用、忘了又没有 UI 出口的凭据；反馈即本次动机。
- **无口令时免旧口令、有口令时必须旧口令**（不加令牌校验）：桌面用户再次遗忘口令时又回到 CLI 死路，问题只解决一半。
- **会话表加 `auth_method` 列，凭「令牌签发的会话」免旧口令**：为一个 UI 分支引入迁移与契约变更；而令牌本身已在手，多存一份来源信息没有额外价值。
- **desktop 模式对所有 admin 会话放开旧口令校验**：任何 admin 会话（含远程登录、被盗 Cookie）都能重设口令，把「短期会话」升格成「长期凭据」，风险不对称。
- **desktop 模式对 loopback 请求免鉴权**：ADR 0016 已否决（`bind_addrs` 可能是 `0.0.0.0`），本次沿用该结论。
- **在壳内（托盘）设置口令**：需要新增壳 UI 与事件通道，而控制台内已有入口，YAGNI。

## 后果

### 正面

- 桌面首启少一步，符合「机器主人」的产品语义；
- 忘记口令有了 UI 内闭环（桌面令牌可直接重设），不再依赖终端；
- `standalone` 的安全姿态与契约零变化；
- 无口令时远程 admin 登录自动 fail-closed，不需要额外开关。

### 负面 / 约束

- 令牌的能力面扩大：从「换取会话」到「可设置 admin 口令」。二者在权限上等价（令牌可换取完整会话），但 ADR 0016 中「令牌是能力」的表述需要据此理解；
- 用户可能长期不设口令，之后远程管理时会发现 admin 登不上 —— 控制台口令区必须常驻「未设置」状态说明（已写进 `admin-console` spec）；
- 存量「引导中」的桌面实例升级后，手上的 `/bootstrap` 链接失效（不再签发令牌），需点托盘「打开控制台」进入后设置口令；`standalone` 不受影响。
