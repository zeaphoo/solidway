# 重启连续性：哪些状态持久化、哪些重建、哪些放弃

状态：accepted（2026-10-19，用户裁决）

## 背景

数据面的状态分布在三个地方，重启时的行为曾经不一致：

| 状态 | 重启后 | 问题 |
|---|---|---|
| Provider 健康（冷却 / 退役） | 由 `provider_health` 回灌 | 已正确 |
| 用量聚合桶 | 丢最后一个 flush 周期 | 无优雅关闭；且**落盘失败即丢弃** |
| 选号指标（TTFB / 失败率 EWMA） | 清零 | 排序退化为"档位 + 轮询" |
| 会话粘性 | 清空 | 每个会话首个请求丢 prompt cache |

## 决策

按"能否重建 + 丢失后果"三分，而不是一律持久化：

1. **不可重建 + 影响正确性 → 持久化 + 种子回灌**
   Provider 健康沿用既有机制（事件上行 → DB → 启动种子）。种子是权威状态，直接覆盖。
2. **可从历史数据重建 → 不建新表，控制面现算后下发**
   选号指标从 `usage_attempt_bucket` 聚合最近 30 分钟（`samples` / `failure_rate` / `ttfb_ms`），
   作为 `ProviderMetricSeed` 随启动配置下发；core 只在本地无样本时采用。
3. **纯优化 / 顺序性 → 不持久化**
   轮询计数器与探针在飞标记重启自愈，不值得引入写路径。
4. **不可重建但只值一次快照 → 优雅关闭时快照**
   会话粘性写入单行表 `runtime_snapshot`，启动时过滤过期条目后作为 `AffinitySeed` 下发。
5. **用量桶必须有收尾**：SIGTERM / SIGINT（含桌面重启路径）走统一收尾（关监听 → 等在途 ≤2s
   → flush → 写快照 → 退出，总预算 5s）；flush 失败时增量**合并回内存缓冲**重试，不再丢弃。

三类种子统一采用规则：**只在本地无记录时采用**（健康种子例外：它是权威状态，直接覆盖）；
非法或过期种子静默忽略，绝不阻塞启动。

## 被否方案

- **一律持久化**（把指标与粘性都写库）：数据面读库破坏纯内存边界；写穿透带来每请求/每 30s 的写放大，收益只是覆盖崩溃这一小概率。
- **事件落盘 + 聚合重算**（零丢失架构）：本仓库用量是统计不是账单，写放大与表设计成本不成比例；真要做分账时再评估。
- **让 core 自己读 DB 恢复**：违反「配置由控制面下发」的边界。
- **收尾失败时以非零码退出**：systemd 会把它当成服务异常并进入重启循环，反而更糟。
- **把粘性写穿透 + 防抖**：覆盖崩溃的增量收益不足以抵消持续写压力。

## 后果

- 计划重启（升级 / 改配置 / 桌面重启）在用量、指标、粘性三方面都是连续的；硬崩溃只丢最后一个 flush 周期与快照（用量 ≤1s，指标与粘性回到聚合/空）。
- 选号指标的种子口径是 `1 − success / attempts`，请求级 4xx 也会拉低它（已知偏差）；要精确需给 `AttemptEvent` 增加 `marked` 字段并给桶加一列，届时再改。
- `runtime_snapshot` 只承载"软状态"，不是业务事实来源：用量、健康、配置的权威仍是各自的表。
- 收尾有 5s 预算，超时强退但退出码保持 0；任何收尾失败只告警，不阻塞、不重试循环。
