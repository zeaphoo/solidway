# ADR 0009 — 创建 Provider 时的服务端同步模型自动拉取

## 状态

已接受（2026-10-20）

## 背景

新建 provider 凭据时模型清单为空 =「不服务任何模型」，用户须手动「获取模型」再保存（或保存后编辑补拉），是纯摩擦。Charles 实测提议（2026-10-20，`tmp/input-provider-auto-discover.md`）：创建保存时若清单为空，自动拉取一次模型清单；失败**不阻断**创建（口径已裁定）。

「不自动拉取」从无显式决策（ADR 与归档 change 均无记录），主 spec「模型清单获取」只规定获取失败「允许先以空清单保存」——本决策是补空白点。真正需要裁决的是**落点**：

1. **服务端创建后同步拉一次**：创建端点内完成拉取与回写，响应即含结果；
2. **前端保存成功后自动调 discover 端点再 PATCH 回写**：复用 H-1 的 `provider_key_id` 回落能力，保存响应快。

评审关注点（输入点名）：并发 / 超时（discover 的 15s 超时会否拖慢保存）、失败信息如何传到界面。

## 决策

1. **落点取服务端同步**：`POST /api/routes/{id}/provider-keys` 创建后清单为空且 `credential_kind = api_key` 时，服务端用该凭据执行一次「模型清单获取」等价逻辑，结果以同名映射写入清单。
2. **失败不阻断**：拉取失败（不可达 / 非 2xx / 解析失败 / 未返回模型 / 超时）→ `201` 创建成功、清单留空；结果经创建响应 `autodiscover`（`ok` / `failed` / `skipped`，`failed` 含可读 `error`）传到界面，失败由界面 toast 提示可稍后手动补拉。
3. **有界等待**：自动拉取独立短超时 **5 秒**（手动「获取模型」保持 15 秒），创建响应延迟有上界；超时按失败处理、不重试。
4. **先落库、后拉取、成功回写**：创建必成与拉取结果解耦，拉取异常不得影响创建；`sync_core` 只下发一次。
5. **不触发**：清单非空、`credential_kind ≠ api_key`（如 `google_service_account`）、任何 `PATCH`（编辑态获取由既有 discover 端点承担）。

## 被否方案

- **前端编排（create → discover → PATCH）**：保存响应快，但整体完成时间相同（拉取总要发生）；引入三段式时序与「已创建未回写」中间态、并发编辑丢失更新风险，失败路径翻倍（discover 成功但 PATCH 失败等）；且管理面无行为变化，与「创建行为 + 自动 discover 语义」的 spec 归属期望不符。
- **后台异步拉取（创建即返回、稍后回写）**：保存最快，但失败信息无法在保存时机 toast（需轮询 / 推送），与已裁定的失败提示口径冲突；引入后台任务生命周期与「拉取结果何时可见」的不确定性。
- **阻塞创建直到拉取完成且失败即创建失败**：违反「先建凭据、后补模型是合法用法」的裁定，慢上游会把保存变成 504 式失败。
- **复用 15s 超时**：保存响应延迟不可接受（评审点名关注）；5 秒足以覆盖正常上游，慢者可手动补拉。
- **创建请求加 `autodiscover` 开关**：为「故意留空」提供逃生舱——暂无真实需求（YAGNI），留待需求出现再加。

## 后果

### 正面

- 主路径（api_key 凭据 + 空清单）保存即得模型清单，消除一次手动往返；
- 失败语义集中、可测：创建响应结构化结果驱动界面提示，无中间态；
- 创建延迟有 spec 级上界（5 秒）。

### 负面 / 风险

- 创建响应最坏多等 5 秒（慢上游），保存按钮等待态变长；
- 「故意留空」无法显式表达，上游可达时清单会被自动填充，需再编辑清空；
- `{base}/models` 不做版本段归一化（保持 discover 端点既有行为）：anthropic / gemini 的 coding-plan base 自动拉取会失败——已在 `docs/future-roadmap.md` 记录待评估；
- `google_service_account` / Vertex 类凭据无自动拉取（discover 是 key 形态鉴权），这类用户仍需手动路径（若将来支持 SA 的模型列举，另立 change）。
