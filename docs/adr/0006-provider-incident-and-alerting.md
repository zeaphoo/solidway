# Provider 故障：事件化记录与分级告警

状态：accepted（2026-10-19，用户裁决）

## 背景

`provider_health` 只保存**当前态**（一行/凭据），回池时整行删除；因此"这个账号昨天挂了三次、一次 40 分钟"永远查不到，无法做排障、SLA 与告警。

同时原有分类把两类**性质相反**的失败混在一起：

- `insufficient_quota` 被当成**永久退役**，但多数厂商按日 / 按周清空配额，到点恢复 → 运维每天要人工点「解除标记」；
- `401` 被当成 30 分钟冷却 + 探针回池，但 key 失效不可能自愈 → 探针白跑；
- `403` 与 `401` 共用同一个原因码，无法区分。

## 决策

1. **故障事件化**：新增 `provider_incident`，一故障一条（`open` → `closed`），记录原因码、严重级别、开始/最近/结束时间、次数、最后状态码。同 provider + 同原因 1 小时内合并，避免刷屏。
2. **处置按"能否自愈"分三类**：
   - 403 / 429 / 5xx / 传输 → 冷却，自动探针回池；401 → 退役，人工恢复；
   - `insufficient_quota` → **长冷却**（`Retry-After` 优先，否则 `quota_cooldown`，默认 6h，上限 7 天），到期探针回池。不猜重置时刻，交给冷却 + 探针。
3. **告警分级**：只对 `degraded` / `manual_action` 的新开故障推送 Webhook；`transient` 只留痕。同 provider + 原因在 `min_interval_minutes` 内去抖；恢复通知可选且仅对已告警过的故障发送。
4. **发送异步**：独立 `tokio::spawn`，5s 超时、3 次退避，绝不阻塞转发；载荷不含任何凭据明文。
5. **历史数据修正**：迁移把 `retired` + `insufficient_quota` 的行改为长冷却，否则老数据永远醒不过来。

## 被否方案

- **只扩展现有状态表**（加 first_seen / count 列）：回池即删除，历史仍然丢；且"多次故障"需要一对多关系。
- **`insufficient_quota` 永久退役**：与"配额按周期恢复"的现实冲突，运维成本高。
- **`401` 继续冷却 + 探针**：探针必然失败，浪费上游请求；且会不断重开同一故障。
- **按"每日/每周"硬编码配额周期**：各厂商不同且不公开，猜错就提前回池或延迟恢复；交给 `Retry-After` + 可配冷却。
- **同步发送 Webhook**：会阻塞事件泵（进而阻塞用量与健康持久化）。
- **初期就做多通道（邮件/Slack/钉钉）**：需要各自的凭证与模板，Webhook 已能覆盖这些（由接收端转换）。

## 后果

- 系统页可看到未解决故障并直接解除；路由详情有横幅；Provider 列表有「近 24h 故障」列。
- `401` 会直接退役：填错 key 的账号会卡住直到人工解除——这是有意的，界面把 `manual_action` 置顶。
- `insufficient_quota` 的最坏恢复时间是 `quota_cooldown`（默认 6h）；需要更快的客户可把该值调小。
- 告警只覆盖 Webhook；P2 再做规则可配（阈值 / 静默窗口 / 多通道）、SLA 统计（可用率 / MTTR）与 incident 的人工备注。
- `403` 的"连续 N 次升级为退役"留到 P2。
