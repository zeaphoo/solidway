# ADR 0015 — 桌面设置：控制台编辑 + 壳执行 + 事件回执

## 状态

已接受（2026-10-23，随 `desktop-prefs-autostart-tray` 落地）

## 背景

需要新增两个桌面生命周期偏好：开机自启动（默认开启、可关闭）与关闭窗口时最小化到托盘（默认开启、可取消）。有三个问题必须先回答：

1. **执行者是谁**：写系统登录项、决定窗口关闭是否退出，只有桌面壳能做；`solidway` 服务没有窗口生命周期，也不知道宿主是哪个 `.app` / 哪个可执行文件。
2. **偏好存哪**：壳在**服务启动前**（登录自启、启动对账）与**服务挂掉后**（bind-failed 错误页、退出策略）都必须能读到。
3. **UI 放哪**：用户要在控制台 `/system` 里改，而控制台是 webview 里的 `http://127.0.0.1:<port>`，只能与服务同源通信。

## 决策

1. **偏好文件 `<data_root>/desktop.toml`，壳是唯一写者**；壳每次启动把生效值物化写入，`solidway` 只读它来渲染控制台。
   - 不变式：文件内容 == 壳实际执行的行为。执行失败不写新值。
2. **编辑面在控制台 `/system`（仅 admin、仅 desktop 模式）**，API 由服务提供：`GET/PUT /api/app/desktop`。
3. **命令通道复用既有 stdout 事件范式**：`PUT` 只做校验并发 `solidway: desktop-apply id=… autostart=… close_to_tray=…`（仅 desktop 模式），壳解析后执行。与 `/api/app/restart` → `restart-requested` 同源。
4. **回执走文件**：壳执行后原子写 `<data_root>/desktop.status.json`（`apply_id` / `ok` / `error` / `applied` / `at`），服务只读并回给控制台；控制台按 `apply_id` 等回执，失败回滚开关。
5. **失败原子**：自启动注册失败时不改偏好文件与关窗策略，回执 `ok=false`；下次启动对账自愈可能的系统/文件漂移。
6. **配套**：单实例守卫（否则「自启 + 手动双击」必然端口冲突）；登录自启固定带 `--hidden`，静默启动失败仍展示错误页。
7. **托盘保留两个勾选项**作为兜底入口（服务不可用时仍能关掉自启动），与控制台共用同一执行管线。

## 被否方案

- **存服务 DB `settings` 表**：壳要读就得带 sqlite 与 schema 知识；更关键的是登录自启时服务还没启动，注册登录项会变成「依赖服务健康」。`bind-failed` 时用户连关掉自启动都做不到。
- **存服务 `config.toml`**：混淆「服务配置」与「宿主偏好」；壳要改它需要保留注释的 TOML 改写，服务改它又要与壳同步 → 双写者。
- **Tauri IPC（`window.__TAURI__`）**：webview 加载的是外部 origin，需要开启 remote-domain IPC 权限；控制台一旦 XSS 即等于拿到壳的原生能力，破坏「纯 Rust、capabilities 为空」的安全基线。
- **壳起本地 HTTP 控制口 + 服务反向代理**：能获得同步回执，但要在无 async runtime 的壳里手写 HTTP server、令牌握手与反代路由；当前毫秒级事件往返已满足需求，YAGNI。
- **只放托盘、不做控制台 UI**：与「设置入口在控制台」的产品要求冲突。
- **服务直接写 `desktop.toml`、壳轮询文件**：双写者 + 轮询；且回执语义仍需额外文件，没有更简单。

## 后果

### 正面

- UI 与 API 都在既有控制台/服务里，复用登录鉴权（admin）、错误体与 i18n；
- 不新增监听端口、不新增跨进程鉴权、不放开任何 JS 能力；
- 偏好与服务解耦：服务挂了也能改自启动、也能按偏好退出；
- 与 `/api/app/restart` 的「HTTP → stdout 事件 → 壳动作」完全同构，认知成本低。

### 负面 / 风险

- 回执是异步的：界面需要「应用中 → 回执」两段式（400ms 轮询，通常一次就命中）；
- 服务侧要读壳写的两个文件（`desktop.toml` / `desktop.status.json`），字段契约由两侧各自实现，需靠 spec 与测试对齐；
- 壳崩溃在「已改系统项、未写文件」之间时，短暂不一致，靠启动对账收敛。
