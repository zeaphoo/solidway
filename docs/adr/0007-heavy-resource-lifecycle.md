# ADR 0007 — 重资源生命周期：停用 / 归档 / 墓碑

## 状态

已接受（2026-10-19）

## 背景

`route` 与 `user` 是聚合根。直接物理删除会同时影响 Provider、API Key、客户端脚本、历史用量、故障记录、运行期粘性与审计归属；现有实现还导致：

- 删除 Route 后，owner 自己的历史统计因 `JOIN routes` 失效而消失；
- 已删除 Provider 的未解决故障无法通过正常入口关闭；
- Route 转移后，历史用量会跟随当前 owner 漂移；
- 删除轻资源后，历史记录只能回退为裸 id。

## 决策

1. **重资源不提供普通物理删除。** `DELETE /api/routes/{id}` 与 `DELETE /api/users/{id}` 改为**不可恢复**的归档语义；可逆操作由「停用」承担。
2. **Route 归档销毁密钥、保留历史。** 归档时写 Provider / API Key 墓碑并删除活行，释放名称、移出数据面、关闭 open 故障、清理粘性；保留 Route 行、用量与故障记录。User 归档禁止登录、删除会话且不可恢复；名下活跃 Route 必须先转移或归档。
3. **名称只在活跃集合内唯一。** `routes` 使用 `(owner_id, name) WHERE archived_at IS NULL` 的 partial unique index；归档路由不占用名称，允许同名归档。
4. **历史归属在写入时固化。** `usage_bucket` 与 `usage_request_detail` 保存 `owner_id` 快照；查询优先使用快照，空值回退当前路由 owner。Route 转移只影响之后产生的用量。
5. **轻资源删除写墓碑。** Provider / API Key 物理删除前写入 `resource_tombstone`，只保留展示身份（名称 / 前缀、父级、owner 快照），不保存密文、哈希或明文。历史查询通过身份视图合并“活行（含归档）+ 墓碑”。
6. **故障记录收尾。** 归档 Route、删除 Provider 时关闭其 open 故障；故障写入校验 Provider 仍存在，避免在途事件复活。
7. **物理清除独立于普通删除。** 本期不提供重资源 purge，也不提供自动保留期清理；归档路由只保留元数据与历史。

## 后果

### 正面

- 历史统计与归属不再依赖活资源是否存在；
- Route 转移可保持客户端无感，同时不污染历史账目；
- 归档路径明确不可恢复；停用承担可逆操作，避免语义混淆；
- 密钥材料在轻资源删除时真正销毁，墓碑不扩大秘密面；
- 数据面只从“未归档”资源构造配置，归档立即停止服务。

### 负面 / 取舍

- 活表查询必须统一过滤 `archived_at`；漏过滤可能把归档资源带进数据面或列表。缓解：CoreConfig 只从 `list_active` 构造，活列表走 repo 层，集成测试覆盖。
- 归档 Route 释放名称，允许同名活跃路由；历史展示必须带“已归档”标记，必要时带短 id 区分同名归档。
- 用量表增加 `owner_id` 并重建唯一键，迁移有成本；同一小时内的转移会形成多个聚合桶。
- 迁移前已物理删除的资源没有墓碑，名称与归属不可恢复，只能回退为 id / “已删除路由”。

## 备选方案

- **写时快照全部标签**：在用量与故障表冗余 route/provider/key 名称。查询更简单，但写路径改造面大，且改名后历史名称仍会漂移，故未采用。
- **全量软删除**：所有资源加 `deleted_at`。可恢复，但每个读路径都必须过滤，密钥必须单独擦除，唯一约束需重建；对轻资源收益低，故只对重资源使用归档。
- **历史表加外键**：`CASCADE` 会删历史，`RESTRICT` 会阻止删除，`SET NULL` 会丢身份，三者都不可接受；历史表继续保持无外键。
